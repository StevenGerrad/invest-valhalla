# 数字人 Agent 迭代、追溯与可视化调研

2026-11-27 · 相关工作调研 4/4

## 我们想问什么

- 我点开第 20 轮的一条长期记忆，能看到它读了哪些案例、每个案例来自哪一期吗？还能看到这条记忆什么时候第一次形成、什么时候改过吗？
- 用户看到一句回答，能不能点开它，看是作者原话、系统归纳，还是按作者的方法做的推演？它真正用的是哪一版知识？
- 我看到一个分数，能否查出哪道题的哪条理由得了分、谁判的、当时系统能看到什么、标准答案又来自哪段视频？
- 其他项目已经做到哪一步？我们有哪些地方可以直接借工具，哪些必须用 Valhalla 自己的记录方式？

## 1. 结论

建议做**同一个可追查的知识库，加三个查看入口**。训练入口看知识如何形成，推理入口看一句回答用了什么，评测入口看分数为什么升降。每个入口都能通过相同的来源和知识版本找到原话，也能从一段有问题的字幕反向找到派生规则、回答和评分。这样做首先方便复核和改错，产品上也能具体展示为什么某条回答值得信任。

已有工作分别覆盖版本、运行记录、事实引用和金融过程审计。**Finer 和 LEDGER 说明「从结果回到证据」已经有人实现。** Valhalla 可以争取的差异是：把这条链延伸到同一作者的**规则版本、按日期冻结的评测、逐句回答及逐项得分**，让四者互相跳转。是否真的改善核查质量，可用找错、定位时间和引用准确率来验证。

两篇综述提供了分类。*From Agent Traces to Trust* 从记录来自哪、记录多细、对象之间什么关系、怎样呈现和怎样验证等角度比较；*Log Analysis for LLM-Based Agents* 按记录生成、整理与分析梳理研究。它们提醒我们，记录了很多工具调用，仍需解释**哪条原话支持哪条主张**。本文按「存什么、能查什么、说明不了什么」比较，第三方结果未独立重跑。 [证据追踪综述](https://arxiv.org/abs/2606.04990) · [Agent 日志综述](https://arxiv.org/abs/2611.23281)

## 2. 已有工具分别能追到什么？

| 研究或工具 | 存什么 | 能查看什么 | 局限与对 Valhalla 的帮助 |
|---|---|---|---|
| **W3C PROV、Web Annotation** | PROV 表示对象、制作活动及派生关系。Web Annotation 定义怎样定位原文范围及版本 | 可表示一条规则由哪些片段、通过哪一次提炼而来，并给出可以重找的位置 | 两套都是公开标准，可以借数据表示。原文是否真的支持结论，要另存审核结果。 [PROV](https://www.w3.org/TR/prov-dm/) · [Web Annotation](https://www.w3.org/TR/annotation-model/) |
| **OpenLineage / Marquez** | 作业、每次运行、输入与输出数据集，可加列级来源 | 查哪些数据集进入哪次处理，沿上游和下游查看影响。Marquez 有图查询和公开界面 | 适合查看某批字幕与索引、训练产物之间的关系。对话原话区间、观点版本和每项判分需要更细的应用记录。 [OpenLineage 数据模型](https://openlineage.io/docs/spec/object-model/) · [列级关系](https://openlineage.io/docs/next/spec/facets/dataset-facets/column_lineage_facet/) · [Marquez 查询](https://marquezproject.ai/docs/api/get-lineage/) |
| **DVC / lakeFS** | 数据文件、配置与命令的版本，或对象存储中的不可变快照 | 回到某次实验的数据版本，比较批次，复用同一个数据快照 | 适合借版本清单与回放思想。恢复了全库版本以后，还需应用记录某条判断用了哪一部分。 [DVC](https://doc.dvc.org/example-scenarios/versioning-data-and-models) · [lakeFS](https://docs.lakefs.io/use-cases/reproducibility/) |
| **OpenTelemetry / OpenInference / Langfuse / Phoenix / MLflow** | 一次运行的步骤、检索输入输出、模型调用、时间、成本和评测记录 | 查一次问答什么时候查库、拿了哪些候选、哪步慢或失败。相关工具也能做版本对照 | 适合做开发排查。召回十段、交给模型三段、回答引用两段，应在应用侧分别关联，避免把出现过的输入都画成支撑依据。 [OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/traces/) · [OpenInference](https://github.com/Arize-ai/openinference) · [Langfuse](https://langfuse.com/docs/observability/best-practices) · [Phoenix](https://github.com/Arize-ai/phoenix) · [MLflow 查看记录](https://mlflow.org/docs/latest/genai/tracing/observe-with-traces/ui/) |
| **Graphiti** | 原始记录、派生关系、有效时间和系统获知时间 | 从派生关系回到原始记录，查看历史改动与支持材料 | 可借双向来源和时间。Valhalla 还需定义长期原则的版本、后续说法是否明确修订，以及一道题为何得分。 [Zep / Graphiti 论文](https://arxiv.org/html/2501.13956v1) |
| **LEDGER** | 保留原始运行记录，将证据与工作流分别变成图节点，再用有含义的边连接主张、动作、文件与检查 | 能围绕回答主张审计依赖、修复动作和验证覆盖 | 与我们的逐句追证很接近。论文通过数据分析与编程示例讲方法。作者知识的历史快照、视频原话和评分的时间隔离要另建。 [LEDGER](https://arxiv.org/abs/2608.18398) |
| **Finer** | 金融原文范围、投资意图、策略和交易动作，记录时间锚点和人工复核 | 审计页支持从动作回到策略过程、意图、字符范围与原文 | 这是金融可视化的直接对照。项目自报 100% 三向可回查率，可用于对比链路覆盖。字幕及作者规则有自己的版本管理，引用语义和评测仍是另一项检查。 [公开仓库与审计页面说明](https://github.com/hongyuanzhou453/finer) |
| **AgentRx / Trial by Trace** | 每个执行步骤、相关证据、预设约束、失败步骤与类型 | 从失败结果问「第一次错在哪一步」；将任务通过与运行流程可靠分别报告 | AgentRx 公布 170 个失败记录及代码，作者自报步骤定位平均相对提升 75%。Trial by Trace 的 3,420 次运行中报告 31.1% 在任务成功时仍违反至少一项运行标准。可借其故障分类和逐步验证。 [AgentRx](https://arxiv.org/abs/2602.02475) · [代码](https://github.com/microsoft/AgentRx) · [Trial by Trace](https://arxiv.org/abs/2610.32285) |
| **BuySideFlow / PIT Discovery** | 记录实际程序步骤和证据使用时间，或审计选中的历史记忆是否越过截止日 | 对输出通过但用了未来信息的情况单独报警，定位到源记录或执行步骤 | BuySideFlow 报告 380 个结果通过且被审计的运行中，193 个有时点问题。适合做 Valhalla 的评测过程复核，而非以答案恰好正确估计知识合规。 [BuySideFlow](https://arxiv.org/html/2611.12966) · [PIT Discovery](https://arxiv.org/abs/2609.12766) |

**应当分别画三类关系。** 知识来源图回答「哪段原文和哪次加工形成这条规则」。一次问答的运行图回答「实际发生了哪些查询和检查」。证券关系图回答「哪些公司、事件、指标相互有关」。首版需要前两类。第三类可以在检索遇到明确瓶颈后再建。参考 [数字人的知识组织](261128_数字人Agent组织形式调研.md)。

## 3. 一条知识必须记录哪些信息？

| 对象 | 建议固定的字段 | 可核查的例子 |
|---|---|---|
| **来源版本** | 稳定来源 ID、原始网址、作者和说话人、实际公开时间、系统收录时间、版本标识与内容校验值 | 同一个 BV 的原始稿与纠错稿均能查看；纠错后旧版本仍能标识 |
| **证据片段** | 来源版本、分 P 与起止秒或文章段落和范围、原文、质量或复核状态 | 只看 12:31–13:10 就能核对某条现金流判断；审计员也可回看相邻上下文 |
| **观点、案例、研究规则的版本** | 内容、标的和相关期间、条件、反例、作者归属、形成与修订轮次、原文或上游记录 | 第 12 期出现一个案例，第 18 轮与另一例合成规则，第 20 轮使用该版 |
| **每次处理的记录** | 实际读过的版本、输出条目、代码与配置、提示与模型版本、人工修订或失败 | 某次回答出错后找到是哪次转录有误、哪次归纳改变了含义 |
| **知识快照** | 本轮可读取的来源、规则、案例与索引的版本清单 | 第 21 期盲测只读取第 20 轮清单，后续入库也不会改变它 |
| **回答主张与评分项** | 主张文本、实际引用的证据、主张类别、知识快照和运行 ID。评分项另存参考证据、评分规则、裁决理由和评分人或模型版本 | 「方向命中、理由缺失」可以分别打开两边原文，而不是只看到 0.5 |

每个对象保留**对象身份与版本身份**。例如「现金流核对规则」是一个对象，第 18 轮与第 25 轮的写法是两个版本。版本更新也保存前后内容。另外记三个不同的时间：**何时公开、系统何时收录、何时进入哪一轮派生知识**。历史回放在今天重做也不能改变当时可用资料的时间条件。

关系类型至少区分以下情况：

1. **被读过。** 这次加工查看了五条案例。
2. **支持／反驳。** 其中两条实际支持新规则，另一条给出失效条件。
3. **进入回答上下文。** 三段检索证据被提供给回答模型。
4. **回答引用。** 模型明确引用了其中两段，各自对应可检查的句子。
5. **作为评分依据。** 评分者使用第 21 期封存原文判定一条理由遗漏。答题侧仍看不到这段材料。

尤其要区分**证据已连上、证据实际支撑主张、证据对答案有多大影响**。第一项可做完整性检查，第二项可比对原文并抽样人工复核，第三项需要移除或替换证据做对照实验。运行记录不等同于模型内部的思考过程。

## 4. 三个入口怎样显示，才能真的用于排查？

| 入口 | 默认显示 | 点进去能看什么 | 一次验收示例 |
|---|---|---|---|
| **训练** | 知识库总体按轮次、来源和知识类型汇总，选中一轮可看新增、修订和失败 | 由规则倒查案例、整理稿、原话与加工记录；由原话正向看受影响的规则和发布版本 | 修正一段字幕，列出受影响的案例及规则。历史快照仍指向原来的版本或明确标记来源失效 |
| **评测** | 总体、题型、批次和时间违规记录 | 总分 → 某一题 → 逐项裁决；并排看答题前允许资料、实际回答、后续原话、评分理由 | 模拟将后期资料提前带入摘要，系统定位泄漏出处。评测记录保留原有提交和新检查结果 |
| **推理** | 答案里各关键句可点开，标明作者原话、系统归纳、外部事实或推演 | 最短路径先回原文，必要时展开案例、规则版本和实际取证步骤 | 用户点「照作者方法，会先核对现金流」，能看到规则及历史引文；公司当前数据从其独立来源打开 |

全局页面适合展示各层覆盖、时间范围、缺出处数和版本变更。局部页面显示当前对象上下游，加筛选和展开，避免把几万条字幕全画在一起。训练、评测和推理使用相同的链接规则。开发者用运行记录排错，普通用户默认看出处、时间和是否属于推演。

## 5. 首版怎样实现和验证

### 数据与界面

- 按当前架构，`ingestion` 负责来源和稳定原文位置，`agent/train` 负责派生知识、加工记录和版本，`agent/evaluation` 保存逐题预测与裁决，`agent/runtime` 保存实际取证和答案主张，`application` 承载界面。场景数据有自己的版本与可用时间。
- 首版可用资料快照、关系表和现有资料文件，并从这些记录生成检索索引。血缘最先保证双向查询和稳定引用。向量内部编号可以更换，公开引用继续使用来源版本与原文范围。
- 记录当时输入、实际用过的证据、答案和评审内容。若云端模型重跑产生不同输出，仍能查看历史原始结果。操作和用户可视区按需要保存，公开展示时只使用获准发布的样例与证据。

### 四组验收数据

| 检查什么 | 如何量化 |
|---|---|
| **路径是否完整** | 每条选定知识、回答主张和评分项，能否沿规定路径到来源。给出覆盖率与中断位置，重复引用和来源下架单列。 |
| **路径是否正确** | 抽样核对标的、说话人、版本、视频时间和原话含义。统计准确位置和真正支持率，避免将「存在链接」算成「引用正确」。 |
| **是否偷看未来** | 用截点之后才出现的原文、摘要和缓存做定向测试，分别核对文档、派生规则和真实运行记录。可借 [BuySideFlow](https://arxiv.org/html/2611.12966) 的时间错误分类。 |
| **是否真的更好排查** | 用相同失败样例，对比只看回答与总分、可看运行记录、可点通完整证据链三种界面。记首次定位到正确错误环节的成功率、时间、点击数和主观信心是否与实际准确性相符。 |

### 可展示的最小闭环

用几期真实视频构建一条长期原则，人工核查它的两处原文。冻结第 20 轮，盲测第 21 期。出现一个遗漏条件的错误后，从评分项点到作者后来原话，再回看当时 Agent 用的规则和案例。最后加入第 21 期并重建下一版，页面展示哪条规则修订、哪些旧结果仍属于历史快照。

做到这一点后，可以用一份样例快照和可运行记录让外部开发者验证「屏幕上看到的来源和代码实际使用的来源一致」。这才是 Valhalla 的全过程展示可以体现的优势。参见 [最接近的项目](261128_数字人Agent相关项目调研.md) 和 [评测与滚动测试](261128_数字人Agent评测调研.md)。
