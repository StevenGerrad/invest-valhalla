# 系统架构划分

Avatar 分为公共运行基础、通用能力接入、数据采集、数字人、场景和业务模块六个一级模块。目前已建立的 `core/`、`integration/` 和 `ingestion/` 位于仓库根目录。表格中的空白单元格沿用上方同列分组。

| 一级模块 | 二级模块 | 职责与边界 |
|---|---|---|
| **公共运行基础 `core`** | **日志 `log`** | 为各模块提供统一日志配置，支持应用、异常及按需启用的访问日志。按 UTC 日期和进程分文件，自动切换和清理历史日志。新采集 CLI 在入口绑定运行 ID，贯穿交互、服务和仓储日志，用于查询任务进度及定位失败。见[日志使用说明](../../core/README.md)。 |
| **通用能力接入 `integration`** | **内容读取 `fetcher`** | 按内容来源组织接入能力，例如 `fetcher.bilibili`。封装各来源的读取细节，按请求返回内容和来源信息。 |
| | **内容转换 `converter`** | 封装 FFmpeg、Whisper 等工具与模型，提供音频提取、语音转字幕和网页正文提取等能力，保留可用于引用的时间戳或段落位置。 |
| | **模型接入 `llm`** | 封装不同模型提供方的鉴权、请求格式、流式响应和错误处理，实现数字人使用的模型接口，支持按配置切换提供方。 |
| **数据采集 `ingestion`** | **交互 `interaction`** | 将内部采集流程封装为 CLI 和未来管理页面可调用的入口，提供配置提交、执行触发、进度查询和结果查看。 |
| | **采集流程 `service`** | 按配置独立执行一次采集，调用外部能力完成获取和转换，并处理校验、去重和失败记录。采集范围可包括博主内容、行业消息、政策、财报和行情。 |
| | **采集实体 `entity`** | 定义来源账号、资料、版本、内容块和证据引用，供采集流程与查询接口使用。 |
| | **资料存储 `storage`** | 当前使用 `data/` 保存博主的原始字幕与纠错处理后的资料。新采集模块通过存储接口接入本地文件实现，后续需要切换 PostgreSQL 时再增加对应实现并导入旧资料。见[采集存储设计](../../ingestion/docs/spec/采集存储设计.md)。 |
| **数字人 `agent`** | **训练 `train`** | 按轮次从博主资料提取、修订和积累可引用片段、观点与研究原则，构建版本化知识。记录各知识层每轮的变更及其依据，产出可评测的候选版本。 |
| | **评测 `evaluation`** | 支持训练中检查、候选版本比较和对指定版本独立评测，检查观点一致性、引用准确性、跨层证据链及历史时点的资料可用性。 |
| | **推理 `runtime`** | 加载指定数字人版本，结合博主知识、场景资料及适用的运行时记忆给出判断。记录关键判断所引用的依据，支持逐层追溯到可核查的原始资料。 |
| **场景 `scenario`** | **数据结构定义 `schema`** | 定义各场景的结构化数据模型，包括字段、类型、单位、时间语义和约束。例如定义证券行情观测记录的结构。 |
| | **知识 `knowledge`** | 组织场景共享的公司、行业、政策、事件、关系和规律，维护来源、适用条件与版本，供多个数字人查询和引用。 |
| **业务模块 `application`** | **对话 `conversation`** | 管理参与者、会话、轮次和结果呈现。首期支持应用内对话，未来可扩展到多人、多数字人及 IM。 |
| | **直接调用 `invocation`** | 提供对话之外的使用方式。页面或外部程序可提交一次业务请求，例如提交符合场景数据定义的行情与消息，调用指定数字人并取得判断、证据和版本信息。 |

运行配置按一级模块集中管理。公共日志配置使用 `core/config.toml`，通用能力接入使用 `integration/config.toml`。登录凭据由调用方单独提供。

单元测试集中在各一级模块的 `test/` 下，并沿用被测源码的相对目录结构。例如 `integration/fetcher/bilibili/client.py` 对应 `integration/test/fetcher/bilibili/test_client.py`。

## 设计目标

### 数字人知识与输出可追溯

数字人输出中的关键判断应能沿实际引用的依据追溯到各层知识。归属于博主的观点或原则应能回溯到公开发布的视频、帖子等一手资料，并定位到具体时间点或原文段落。数字人针对新情况作出的推断，应标明所用的博主知识、场景资料和推断结论。

- **训练**。每轮记录各知识层新增或修订的条目及其前后版本，并保存每条产物引用的上游知识或原始资料的标识、版本和引用位置。
- **推理**。每次运行记录数字人版本、实际读取的知识与资料版本，以及每条关键判断所引用的依据。记录应能区分进入上下文的资料与支撑具体判断的资料。
- **评测与可视化**。评测使用同一套追溯记录检查证据链是否完整、引用是否支持判断。训练与推理应在运行过程中持续记录可查看的依赖关系，并保留历史记录，支持按训练轮次、知识版本或推理记录查看和对比，直至打开可核查的原始资料。

### 滚动评测与质量监测

首期以同一博主持续发布的证券投资内容为语料，其研究范围集中、分析风格相对稳定。按原始发布时间滚动评测，用前期资料构建并冻结数字人知识版本，预测下一批内容中的研究判断，以博主随后公开的观点及理由为评分依据。锁定成绩后再将该批资料入库，继续测试下一批。已测批次不再作为未见样本重复计分。

持续监测各版本的观点与理由一致性、引用准确性和质量退化。逐题保留当时的知识版本、预测、原文依据与评分理由，支持复核和排查。
