# 项目代码规范

## 注释

- 说明正文和代码注释使用中文。代码标识符使用英文，API 名称、字段名及通用缩写保留原文。
- 类的说明应写清职责、适用范围和模块边界。函数与方法的说明应覆盖用途、参数、返回值及调用方需要了解的异常或特殊行为。
- 类的每个字段都应有独立注释，尤其是实体类。说明字段的业务含义，并在有需要时写清标识的归属、值的单位、默认值或为空的含义。新增或修改字段时同步更新注释。
- 在方法内的关键代码块旁用中文注释说明处理原因、触发条件和结果。外部数据格式差异、配置优先级、状态转换、失败恢复和持久化等细节应写到足以让评审者理解实现取舍。测试注释说明用例意图和容易误读的数据，行为变化时同步更新注释。

Python 的文档字符串格式、包文件和测试执行方式见 [Python 代码规范](Python代码规范.md)。

## 模块与实现

- 按[系统架构划分](../spec/系统架构划分.md)分配职责。相关逻辑保留在拥有该职责的模块内，跨模块通过公开接口和明确的数据类型调用。第三方 SDK、协议和格式转换细节由接入模块封装。
- 保持依赖方向清晰，避免循环依赖。优先复用现有契约与实现，在确有多个实现或需要隔离外部依赖时抽象接口。
- 同一一级模块内跨子模块复用的类统一放在该模块的 `common/` 目录中。`common/` 与 `service/`、`entity/` 等目录同级。
- 保持类与方法职责集中，使用领域术语命名。外部调用、文件写入及失败恢复应有清晰边界，调用方可以判断结果是否完整。
- 按实际需要创建文件和目录，等有代码、配置、文档或测试内容时再建。仅为占位的空文件或空目录无需加入项目。

## 服务接口与数据边界

- 根据交互需求和现有调用链设计接口。重构已有功能时，先核对旧入口的实际操作、输入、结果和失败处理。摘要、部分字段读取等查询优化由具体用例和性能瓶颈驱动。
- 定位已保存的实体时，服务方法接收 `XxxIndex` 身份接口，例如 `AvatarIndex` 和 `MaterialIndex`。领域实体实现对应接口，可供后续操作使用的服务输出也可以实现同一接口。服务通过索引取得底层 ID。创建和修改所需的业务字段通过参数对象提交。
- 服务的业务入参使用 `XxxParam`，单字段也适用，例如 `UpdateAvatarParam`。目标索引和平台等定位参数直接传递。服务交付 DTO，按内容使用 `Info`、`Detail`、`Page` 或 `Result` 等命名，嵌套内容同样使用输出类型。在服务包的 `dto/` 中，为每个服务接口创建一个 `<服务接口名>_dto.py` 文件，集中放置该服务的入参和输出。文件名使用小写下划线形式，例如 `avatar_service_dto.py`。多个服务共用的类型复用同一份定义。
- 实体转 DTO 时，由目标 DTO 自身的静态方法或工厂方法（如 `from_entity()`）提取并组装字段。转换逻辑集中在目标 DTO 内维护。
- 只有执行动作的单条命令成功时可以没有返回值，例如删除资料。接口文档应声明其可预期的异常和触发条件，交互层负责呈现失败。查询应写清查不到单条资料或匹配列表为空时的返回约定；有跳过、无需加工等正常分支时，可以返回带状态的结果。
- 批量方法以 `batch_` 加单条方法名命名，例如 `collect_material` 与 `batch_collect_material`。批量结果按输入顺序逐项返回。将可预期的单项失败记录在该项结果中，继续处理其他项。批次共用的参数无效时，直接报错。
- Repository 以领域实体为读写单位，具体实现负责文件布局、序列化和存储对象转换。服务层负责采集、加工、跳过或重试等业务流程。
- 接口文档要写清默认策略、空结果的含义和操作影响的范围。例如，删除加工稿只移除加工稿，保留原始资料。

## 日志

- 交互层、服务层、持久化层和外部能力接入层都应记录可追溯的日志。关键操作和失败应能关联到同一次任务，便于定位问题发生在哪一层。

## 单元测试

- 单元测试集中在所属一级模块的 `test/` 下，沿用被测源码的相对路径。例如 `integration/fetcher/bilibili/client.py` 对应 `integration/test/fetcher/bilibili/test_client.py`。
- 测试文件按可验证的职责组织，相关用例可以放在同一文件。模拟网络和第三方服务，文件测试使用临时目录。真实服务验证与跨模块流程测试在有实际需求时独立运行。
